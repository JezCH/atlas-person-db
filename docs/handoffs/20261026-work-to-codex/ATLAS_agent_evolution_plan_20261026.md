# ATLAS 에이전트 운영 발전 계획
작성: 2026-10-26 KST  
범위: 기존 ATLAS 자동화를 본사업 산출물의 완성까지 연결하는 운영 계획. 이번 요청에서는 설정 변경·모델 위임·코드 수정·PR 작성·병합·배포를 실행하지 않음.

## 1. 목표와 결정
사용자는 목표와 중요한 결정을 전달하고, 에이전트는 필요한 자료와 도구를 찾아 실행·검증·저장·인계까지 이어간다. 실제 성과는 Place 복원, 승인된 인물 등록, 데이터 결손 수정, 필요한 UI 기능의 사용자 도달로 판단한다.

채택할 구조는 **총괄 하나 + 업무별 매뉴얼과 도구 + 필요한 경우의 분리된 실행·검토**다. 역할의 개수와 실제로 실행 중인 에이전트의 수를 구분한다. 여러 모델의 상시 협의나 새로운 관리 시스템 구축을 선행조건으로 두지 않는다.

에이전트는 목표를 받고, 현재 상태를 관찰하고, 도구로 행동하고, 결과를 확인한 뒤 다음 행동을 고르는 실행 주체다. 업무 매뉴얼은 행동 지침, 스킬은 재사용 가능한 업무 방법, 도구는 실제 실행 수단, 예약은 실행을 깨우는 장치다. 파일을 만들어 두거나 예약을 등록했다는 사실만으로 업무 완결 능력이 생기지는 않는다.

첫 영상의 로컬 출근 비서 실습은 영상 속 예시다. 그것을 사용자가 ATLAS에 선택한 로컬 운영 조건으로 해석하지 않는다. ATLAS의 PC 없이 클라우드에서 진행한다는 기존 방향을 유지한다.

영상에 등장하는 모델 우열이나 월 구독료만으로 모든 외부 서비스 비용이 해결된다는 주장은 이 계획의 전제가 아니다. 23개 역할도 23개 독립 실행 프로세스 또는 24시간 가동을 입증하지 않는다.

## 3. 이번에 확인한 현재 상태

- main의 AGENTS.md에는 표적 코드 검색, 정적 의존성 탐색, 업무별 스킬, 검증된 수정 경험 검색이 연결되어 있다.
- PR #2593은 병합되었으며, #2590·#2591은 그 통합 PR로 대체되어 닫혔다. 다시 구현하거나 병합할 대상이 아니다.
- Issue #2603의 기록은 실제 선택→Codex 명령→인증된 패치→결과 PR→Integrity CI→결과 기록의 1회 성공을 담고 있다.
- 그 결과 PR #2611은 현재 OPEN / ready for review / 미병합이다. 최신 댓글의 다음 조건은 유지관리자의 의미 검토와 명시적인 병합 권한 판단이다. 이전 Draft 설명을 현 상태로 복사하지 않는다.
- Codex 작업 등록부는 enabled=false이고 승인된 작업은 0개다. 기존 1회 성공은 상시 모델 실행 권한이 아니다.

### 현재 실제 예약과 우선순위
- 기존 “ATLAS 단계별 지속 개발” 예약 하나가 활성 상태다. 저장된 주기는 매시간이다. 다른 ATLAS 실험 예약들은 조회 결과 비활성이었다.
- 해당 예약의 최신 프롬프트는 Place #2476 복원 준비를 현재 납품 단위로 지정하며, 자동화 보조 도구 확대와 파일럿 #2603을 이 실행의 대상으로 삼지 않는다.
- 2026-10-26 06:00 KST 예정 회차는 플랫폼상 completed이고 결과가 저장되어 있다. 이 표시는 본사업 전체 완료를 뜻하지 않는다.
- 상세 조회에서 next_run_time은 null이었다. 매시간 규칙과 활성 설정은 확인했지만 정확한 다음 실행 시각을 별도로 확정하지 않았다.
- 유튜브 전용 발굴 인프라는 폐기된 작업이다. 과거 수집을 다시 시작하지 않으며, 이미 사용자가 선택한 인물 초안은 보존한다.
- person-only UI 초안은 PARKED_PRIORITY_REVIEW다. 자동으로 우선순위를 되돌리지 않는다.

### Place 체크포인트 v9 실제 파일

| Source 27개 | 10개 STRUCTURALLY_VALID_EVIDENCE_HOLD, 17개 HOLD_MISSING_CANONICAL_URL | 10개 모두 역사적 검토 승인되었다는 뜻이 아님 |

원본 장소 기능에는 id 필드가 없다. 보존해야 할 20개 Place·27개 Source의 UUID와, 기존 작성기가 부여하는 장소 기능의 의미 키를 구분한다. 존재하지 않는 기능 UUID를 “복원”한다고 만들지 않는다.

구체적인 검토 사례: 1911년 간행 출처만으로 1922년 수도 지위 종료를 입증할 수 없다. URL 확보·구조 검사와 역사적 주장 검증은 별도다.

## 4. 운영 구조와 책임
| 역할 | 책임 | 실제 실행 방식 |
|---|---|---|
| 사용자 | 목표·범위·우선순위, 비용·파괴적 변경·운영 적용의 필요한 승인 | 하나의 대화에서 결정 |
| 총괄 | 최신 지시 해석, 본사업 선정, 필요한 도구 선택, 결과 취합, 구체적인 승인 안건과 재개점 제출 | 기존 Work 실행이 담당 |
| 실무 | 출처 대조, payload 작성, 실제 기존 소스 수정, 필요한 검증 | 동일 실행자가 업무별 스킬로 처리하는 것이 기본 |
| 검토 | 출처가 주장 전체를 뒷받침하는지, 입력·코드·완료조건이 맞는지 검사 | 원본·실행 결과·기존 테스트 우선. 필요하고 허용될 때 별도 맥락의 검토 |
| 실행 기반 | 일정에 따른 기동, GitHub 변경 이력·CI, canonical writer | 기존 예약·연결 도구·워크플로우 재사용 |

세 역할이 있다고 모델을 세 번 호출해야 하는 것은 아니다. 여러 AI의 동의는 독립된 역사적 증거나 운영 read-back을 대신하지 않는다. 총괄 역할은 프로젝트 전체 쓰기 잠금을 만들지 않는다.

향후 독립적인 출처 검토를 병렬화하더라도 서로 다른 자료를 읽는 준비 단계만 분리하고, 같은 UUID·파일·공유 계약의 최종 변경은 현행 낙관적 동시성 규칙을 따른다. 이번 계획 수립 중에는 하위 에이전트를 실행하지 않았다.

## 5. 실행과 인계 계약
기존 예약은 유효한 현재 납품 단위와 체크포인트를 이어받는다. 매 회차 전체 프로젝트나 과거 대기열을 다시 조사하지 않는다.

1. **현재 지시 확인:** 최신 사용자 지시, 작업의 활성 포인터, 체크포인트 버전, 직접 관련 경로·입력의 변경만 확인한다.
2. **완료 가능한 산출물 확정:** 무엇이 달라져야 하는지와 완료 증거를 정한다. 함수 하나·테스트 하나·보고서 하나를 자동으로 납품 단위로 삼지 않는다.
3. **실제 실행:** 원본을 대조하고 입력 또는 기존 소스를 수정한다. 독립적으로 가능한 준비는 계속한다.
4. **검토:** 구조 검사, 출처의 주장 지원 범위, 실제 실행 결과를 구분한다. 위험에 필요한 최소 검증을 한다.
5. **구체적인 경계에서 인계:** 허용된 범위는 끝내고, 필요한 권한이 있는 변경만 승인함에 올린다.
6. **저장과 다음 회차:** 현재 공식 체크포인트를 갱신하고, 실제 끝난 부분·미완료 항목 ID·정확한 다음 행동을 남긴다.

인계에는 기존 파일에 다음 정보만 충분히 담는다: 사용자 목표, 현 권한 범위, 원본/코드 버전, 정확한 대상, 결과물, 실행·검증 증거, 남은 근거 공백, 필요한 승인, 다음 행동. 새 중복 등록부는 만들지 않는다.

공유 체크포인트가 다른 실행에서 갱신되었다면 버전을 확인하고 자신의 변경만 결합한다. 오래된 ZIP 전체로 최신 결과를 덮어쓰지 않는다. 스크래치 작업폴더는 회차 간 보존을 가정하지 않는다.

## 6. 첫 납품 단위: Place #2476 복원 준비 묶음 완성
새로운 자동화 파일럿을 시작하는 대신 현재 본사업으로 운영 구조를 검증한다.

### A. 기존 작업 재사용
v9의 original-manifest, restoration-inputs, source-review, source-assertions, writer-contract, 검증 기록과 exact-place-transport.patch를 이어받는다. 관련 코드가 바뀌지 않았다면 Source 경로와 워크플로우 39개 조사를 반복하지 않는다.

### B. 근거와 입력을 함께 완성
- 남은 17개 Source의 URL·원문·locator를 항목별 대조한다.
- 이미 구조 검사를 통과한 10개도 필요한 역사적 주장·기간 지원 범위를 별도로 확인한다.
- 전체 23개 장소 기능에 근거를 연결하고, 확인되지 않은 역할·시기·종료연도는 정확한 이유와 함께 HOLD로 분리한다.
- 원문을 못 찾은 항목은 미확인으로 남긴다. 찾기 어려운 한 출처가 다른 확인 가능한 항목을 막지 않게 한다.
- Source exact-before/after와 충돌 조건을 담은 실행 계획 envelope를 완성한다. 운영 부재는 실제 운영 사전검사 전까지 제안된 조건이다.

### C. 실제 작성 경로의 병목 해결
- 보존 UUID 삽입 기능과 현재 실행기의 연결 공백을 관련 최신 소스와 대조한다.
- 재사용 가능한 기존 작성기를 연결하는 최소 수정으로 해결할 수 있으면 그 소스에 통합하고 집중 검증한다.
- create_place로 UUID를 새로 만들거나 한국어 이름을 임의 작성하여 우회하지 않는다.
- Source→Place→장소 기능→별도 Runtime compile→read-back의 의존 순서를 구체화한다.

### D. 하나의 검토 가능한 묶음으로 전달
납품물은 실제 입력/payload, 27개 출처의 대조 상태, 23개 주장별 READY/HOLD 근거, 현행 writer 연결과 필요 수정, 집중 검증 결과, 운영에서만 확인할 preflight·승인·복구 조건이다.

- 오프라인에서 확인 가능한 중복·참조·지원 필드·UUID 보존과 실행 순서를 확인한다.
- 외부 Vercel 전달 설정 미확인은 별도 REMOTE_DELIVERY_HOLD로 둔다. 원격 전달 대기가 오프라인 준비 완성을 막지 않는다.
- 안전한 원격 경로가 검증되면 권한 범위 안에서 해당 결과를 전달한다. 현재 제한을 추정으로 해제하지 않는다.
- HOLD 항목이 남아도 그 이유와 누락 증거가 정확히 특정되고, 가능한 나머지 입력이 완성되어야 “준비 묶음 완성”으로 보고할 수 있다.
- 준비 묶음의 완성은 전체 복원 READY나 운영 복원 완료를 뜻하지 않는다.

| 별도 Codex·외부 모델 호출 | 현재 활성 예약에서는 금지 유지 | 과거 1회 승인을 상시 승인으로 확대하지 않음 |
| PR 병합 | 해당 PR의 명시된 리뷰·병합 권한과 필수 체크 확인 | #2611은 별도 유지관리자 검토 경계 유지 |
| Production 조회·Apply·Compile·배포 | 현재 금지/승인 조건 유지 | 오프라인 성공으로 운영 성공을 주장하지 않음 |
| 삭제·retirement·동일인 통합·스키마 변경 | 해당 작업별 명시 승인과 복구·충돌 검증 | 묶음 승인이나 낡은 목록으로 확대 금지 |
| 새 비용·유료 API·충전·플랜 변경 | 명시 승인 필요 | 프롬프트나 일일 실행 횟수가 계정 과금 상한을 보장하지 않음 |

승인함은 새 웹앱 대신 기존 결과 보고와 관련 PR/이슈를 사용한다. 안건에는 정확한 대상, 바뀌는 상태, 검토 가능한 diff/payload, 증거, 남은 위험, 복구 경로, 요청하는 권한만 넣는다. 승인받기 전에 준비 가능한 작업은 완료한다. 승인 후 대상이나 의미 있는 입력이 변하면 영향 부분만 다시 검증한다.

## 8. 실패·중복·비용 처리
- **명령 제출 후 기록만 실패:** 이미 받은 코드·검증 결과를 보존하고 기록 단계만 진단한다. 새 모델을 재호출하지 않는다. #2611 후 journal 403 사례의 교훈을 그대로 재사용한다.
- **쓰기 결과 불명확:** 기존 계약이 허용하는 정확한 읽기 확인을 이용한다. 쓰기 재시도를 자동으로 추가하지 않는다.
- **출처가 주장 일부만 지원:** 날짜·역할별로 HOLD를 표시하고 다른 항목 준비를 계속한다. 확실하지 않은 부분을 그럴듯한 값으로 채우지 않는다.
- **공유 상태 변경:** 충돌한 UUID·파일·직접 계약만 갱신한다. 프로젝트 전체를 다시 시작하지 않는다.
- **HTTP 402·권한 거절:** 같은 요청을 반복하거나 다른 인증 경로로 우회하지 않는다. 영향 없는 준비 작업만 이어간다.
- **실행은 완료됐지만 산출물이 늘지 않음:** 수행 난이도가 낮다는 이유로 주변 결함을 고르지 않는다. 두 회차 연속 납품 범위가 늘지 않으면 정확한 병목을 해결하거나 실행 가능한 본사업으로 전환한다.
- **토큰·무료 사용량:** 관련 맥락만 읽고, 스크립트가 확정할 수 있는 형식 검사는 스크립트에 맡긴다. AI 여러 명의 상시 회의·1분 사용량 polling·불필요한 CI/배포를 추가하지 않는다.

## 9. 발전 순서와 통과 조건
| 순서 | 수행할 일 | 다음 단계로 가는 증거 |
|---|---|---|
| 1 | 현재 Place 복원 준비 묶음을 완성 | 재사용 가능한 실제 입력, 주장별 근거/HOLD, 작성 경로, 필요한 검증과 다음 승인 안건 |
| 2 | 다음 기존 예약 회차에서 같은 묶음을 재개 가능한지 확인 | 원본 재조사·중복 생성 없이 최신 결과를 읽고 정확한 다음 변경을 수행한 기록 |
| 3 | 원격 전달·운영 권한의 실제 경계 해결 | 안전한 전달 경로, 명시 승인, 대상 상태의 fresh preflight |
| 4 | 승인된 작업의 운영 완료 | canonical apply·compile/read-back 또는 실제 변경 UI 확인 등 작업별 종료 증거 |
| 5 | 유효한 본사업이 있을 때 반복·독립 준비 병렬화 | 중복·충돌·사용자 재지시 감소와 실제 완료 증가가 확인됨 |

현행 매시간 예약의 빈도는 이번에 변경하지 않았다. 이후 변경한다면 실행할 수 있는 잔여 작업과 계정 사용량을 근거로 기존 예약을 조정한다. 모든 일이 외부 승인을 기다리면 같은 차단을 매시간 재조사하지 않도록 기존 예약의 대기/중지 조건을 검토한다. 새 예약이나 자기호출 체계로 보완하지 않는다.

PR #2611의 검토·병합 판단은 이 본사업과 독립된 남은 안건이다. 이 PR의 처리가 Place 준비의 선행조건이 되거나 새 자동화 개발을 연쇄적으로 시작시키지 않게 한다.

## 10. 사용자에게 보여줄 결과와 성공 판정
매번 다음 네 가지를 짧게 보고한다.
1. 이번에 실제로 완성한 데이터·기능·인계물과 증거
2. 사용자가 체감할 상태 변화와 현재 완료 단계
3. 남은 정확한 근거·권한·운영 차단
4. 다음 행동 또는 구체적인 승인 안건

평가 기준은 PR 수·테스트 수·회차 수가 아니다. 미완성 납품 단위의 감소, 이전 결과를 다시 설명하지 않고 이어간 사례, 원본과 대조된 주장 범위, 중복·재작업, 사용자에게 필요한 재지시/승인 횟수, 실제 사용량을 본다. 분모나 과금 정보가 없으면 성공률·절감률·0원 운영을 만들지 않는다.

최종 목적은 사용자가 매번 “다음 단계 해”라고 지시하지 않아도, 허용된 본사업을 완료하고 정말 필요한 결정만 받는 상태다. 새 체계의 첫 성과는 Place 복원 준비 묶음의 완성으로 판단한다.
